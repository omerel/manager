## Context

חלק א׳ הותיר תשתית שחלק ב׳ עומד עליה: `parseTable`, זיהוי כותרות + פרשנות סוכן (מבנה ופורמט-תאריך), התאמת זהות אכופה, ומצב-תצוגה-מקדימה שחי ב-AgentRun כך שהאישור מבצע את מה שהוצג. וקיימת תשתית שנבנתה לחילוץ מסמכים ומתגלה כמתאימה בדיוק: `ExtractionProposal` — הצעות `{נוכחי, מוצע}` צמודות לאדם עם יישום פר-פריט.

הנתון החדש הוא היעדים: ערך של אירוע נקודתי חי ב-`PointProgress` (קיום השורה = בוצע, `doneOn` = מתי), וערך מדד ב-`MetricReading`. שניהם מפתחים אל **עותק** התכנית של האדם — ולכן מיפוי עמודה חייב לדבר בתוויות, לא במזהים.

## Goals / Non-Goals

**Goals:**
- קובץ שבועי → הצעות מדויקות, מינימליות, שקופות — ואפס כתיבה בלי אישור שדה.
- מיפוי שנקבע פעם אחת ומחזיק שבועות; שינוי מבנה מטופל בלי לזרוק את המוכר.
- תיקון ידני במערכת לעולם אינו נדרס בשקט.

**Non-Goals:**
- יצירת אנשים (חלק א׳), מחיקת אנשים, שינוי שיבוץ. עדכון ערכים בלבד.
- חוות-דעת, ראיונות, אירועים מחזוריים — לא יעדים.
- ריבוי מיפויים (קובץ-אב אחד, מיפוי אחד).
- חלק ג׳ (לוג תנועות) — שינוי נפרד.

## Decisions

### שני מודלים חדשים, גבול ברור ביניהם

```prisma
model ImportMapping {   // אחד גלובלי לחתימת-כותרות; נערך, לא משוכפל
  headersHash  String  @unique   // כותרות מנורמלות, ממוינות, מגובבות
  mapping      Json               // [{header, targets: ColumnTarget[]}] — רב-יעד
  dateFormats  Json               // פרשנויות פורמט שנשמרו עם המיפוי
}
model ImportSnapshot {  // ההיסטוריה: קובץ + שורות לדיף הבא
  filename, uploadedAt, uploadedById
  headersHash  String
  rows         Json               // ה-snapshot שהדיף הבא רץ מולו
  filePath     String             // הקובץ עצמו, תחת uploads
}
```

המיפוי גלובלי — הכרעת המשתמש: מערכת-אב אחת, כל משא״ן חולק. חתימת הכותרות היא המפתח, כך ש«אותו מבנה» מזוהה גם אם הקובץ נקרא אחרת.

### יעד עמודה מדבר בתוויות, ורב-בחירה היא הכלל

```
ColumnTarget (הרחבה):  שדות הכרטיס מחלק א׳
                     | point:<תווית אירוע>      ← תאריך הביצוע
                     | metric:<תווית מדד>       ← הערך המצטבר

עמודה «הסמכת נשק» → [ point:הסמכת רובים (חוקר), point:הסמכה בסיסית (מהנדס) ]
                       │
בזמן עדכון, פר-אדם:    └─ מיושם רק על היעד שקיים בתכנית *שלו* — השאר מדולגים
```

תווית ולא מזהה, כי התכניות הן עותקים: המיפוי נקבע מול התבניות, והיישום מוצא את האירוע בעל אותה תווית בעותק של האדם. אדם שאף יעד אינו בתכניתו — התא פשוט לא רלוונטי לו, בלי רעש.

### הדיף דו-שלבי, וכל שלב עונה על שאלה אחרת

```
הקובץ החדש ──┬── מול snapshot קודם ──▶ מה השתנה *בקובץ*?   ← מסנן רעש
             │      (אין קודם? הכול עובר)
             └── מול המערכת ──────────▶ מה שונה *מהקיים*?   ← יוצר הצעה

הצעה קמה רק כששני השלבים עוברים. מכאן נובע מעצמו:
  ערך שתוקן ידנית במערכת + קובץ שלא השתנה  → אין הצעה. התיקון שורד.
  ערך שהשתנה בקובץ אך שווה למערכת          → אין הצעה. אין רעש.
```

הריצה הראשונה — אין snapshot — משווה הכול מול המערכת: זו בדיוק ההזנה הראשונית שהרעיון מתאר.

### שינוי מבנה: לשאול, לשמר את המוכר

חתימה לא-מוכרת ⇒ מסך ביניים לפני כל דבר: «המבנה שונה מהקובץ הקודם — עמודות חדשות: X, Y; עמודות שנעלמו: Z». המשתמש בוחר להמשיך; עמודות מוכרות שומרות את מיפוין, החדשות עוברות זיהוי + סוכן וממופות לאישורו. אין מיפוי-מאפס כפוי, ואין המשך שקט.

### ההצעות רוכבות על ExtractionProposal, בשלוש הרחבות

מודל קיים, פאנל קיים, יישום-פר-פריט קיים. ההרחבות: (1) `applyItem` לומד `point:`/`metric:` — מציאת היעד בעותק של האדם, upsert של Progress/Reading; (2) פריט מחיקה — `proposed` ריק עם דגל, יישומו מוחק Progress/Reading או מרוקן שדה מותאם; מוצע **רק למה שרשאי להיות ריק**, תא חובה שהתרוקן → אזהרת שורה; (3) מסך סקירה מרכזי ב-`/hr` שמקבץ את הצעות הריצה לפי אדם — במקום ביקור בכרטיסים — עם אישור/דחייה פר-שדה, «אשר אדם», «אשר את כל המסומנים». האישור הוא אותו `resolveProposalItem`; המסך הוא תצוגה, לא מסלול כתיבה שני.

ההצעות נוצרות רק לאנשים בתחום העריכה; אדם שבקובץ ואינו במערכת — דילוג שקט, כהכרעת המשתמש.

### מה נכתב מתי

העלאה ודיף — קריאה בלבד. ההצעות נכתבות כרשומות הצעה (זה טיבן — טיוטה הממתינה ליד). ערכי אדם משתנים אך ורק באישור שדה. ה-snapshot וההיסטוריה נשמרים בסיום הסקירה — «לאחר אישור השינויים», כלשון הרעיון — כך שריצה שנזנחה באמצע אינה נהיית בסיס-הדיף של השבוע הבא.

## Risks / Trade-offs

- **מחיקות** הן ההצעה המסוכנת → מוגבלות לרשאי-להיות-ריק, ברירת מחדל לא-מסומנת במסך האישור, ותמיד פר-שדה.
- **תווית אירוע ששונתה בתבנית** מנתקת מיפוי בשקט → המסך מציג יעד-בלי-תאימות («אף תכנית אינה מכירה ׳הסמכת רובים׳») כאזהרה על המיפוי.
- **snapshot גדל** (קובץ שבועי × שנים) → נשמר האחרון בלבד לדיף + הקבצים בהיסטוריה; לא נשמרות כל השורות לכל שבוע.
- **שני משא״נים מעלים באותו שבוע** → המיפוי משותף אך ריצת סקירה היא פר-משתמש; ה-snapshot מתעדכן בסיום סקירה, והשני יקבל דיף מול העדכני. מוצהר, לא ננעל.

## Migration Plan

1. מיגרציה: שני המודלים; אין נגיעה בקיים.
2. אין נתונים להעביר; הריצה הראשונה היא ההזנה הראשונית מטבעה.
3. חזרה לאחור: הסרת הטאב והמודלים; הצעות פתוחות נמחקות עם המודל שלהן — ערכים שאושרו כבר נכתבו ונשארים.
